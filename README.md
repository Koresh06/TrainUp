# TrainUp

Telegram-бот для записи на тренировки, оформления заявок на программы тренировок
и консультации с тренером. MVP разрабатывается под одного тренера, архитектура
сразу закладывает возможность подключения других тренеров в будущем (по подписке).

## Статус

🚧 MVP функционально готов, идёт полировка перед демонстрацией.

**Клиент** (вход только по инвайт-ссылке тренера, `/start <token>`):
- Регистрация с настраиваемой анкетой тренера (здоровье, цели, свои вопросы)
- 📅 Запись на занятие: календарь → время → подтверждение (лимит активных записей,
  прошедшие слоты скрыты), уведомление тренеру с анкетой клиента
- 📋 Мои записи — ближайшие тренировки и их статус (отмена/перенос — через тренера
  или кнопкой в напоминании)
- 🏋 Программа тренировок, 💬 Консультация — заявки тренеру
- ✉️ Обратная связь: обратный звонок, сообщение тренеру, ❓ FAQ
- 📝 Моя анкета — просмотр и обновление ответов
- Напоминание о тренировке (с кнопками подтвердить/отменить) и напоминание
  «запланируйте следующую тренировку» через 3 дня после занятия

**Тренер** (`/trainer`): онбординг (рабочая группа выбирается системной кнопкой
Telegram) и подписка, бронирования (подтверждение,
отмена, перенос, история), постоянные клиенты с еженедельным автосозданием,
📨 заявки клиентов со статусами (и кнопками прямо в рабочей группе), клиенты
с анкетами, статистика с графиками (тренировки, доход, загрузка по дням и часам),
профиль, 💎 подписка с описанием возможностей и выгодой длинных тарифов; настройки — расписание (шаблоны + вместимость),
🚫 блокировка дней/слотов, цены, лимиты записи, вопросы анкеты, напоминания;
❓ помощь — FAQ с правилами пользования ботом.

**Подписка тренера.** Новый тренер сразу после регистрации получает бесплатный
пробный период (`APP_CONFIG__BUSINESS__TRAINER_TRIAL_DAYS`, по умолчанию 7 дней,
0 — выключить); оплата во время триала начинается после его окончания.
Предупреждения за 48 и 3 часа до окончания (настраивается
в `.env`, для триала — свои тексты), по окончании — кабинет тренера и запись его клиентов закрываются,
в сообщении кнопка «💳 Продлить подписку» → выбор тарифа. Продление добавляет
срок к текущей подписке.

**Оплата подписки** (цены тарифов — в USD). Способы оплаты — стратегии
`PaymentProvider` в реестре `PaymentProviderRegistry`; тренер видит только
включённые в `.env`:
- 💳 **ЮKassa** — сумма пересчитывается в RUB по `USD_TO_RUB_RATE`; подтверждение
  только webhook'ом (`webhook`-сервис, FastAPI), статус перепроверяется в API ЮKassa;
- ⭐ **Telegram Stars** — инвойс в XTR по `USD_PER_STAR`, подтверждает `successful_payment`;
- 🤝 **Через администратора** — админам приходит заявка с кнопками
  «✅ Оплата получена / ❌ Отклонить», подтверждение сразу активирует подписку;
- 🧪 тестовая оплата — только при `APP_CONFIG__PAYMENT__TEST_MODE=True` (разработка).

Новый способ оплаты = новый класс в `src/infrastructure/payment/providers/` +
одна строка регистрации в `providers/services.py`; use case'ы, диалог оплаты и
подтверждение не меняются. Подтверждение идемпотентно (`SELECT … FOR UPDATE`):
повтор webhook'а или двойное нажатие не выдаст подписку дважды.

**Админ** (`/admin`, `ADMIN_IDS` из конфига):
- 📊 статистика за сегодня/неделю/месяц/всё время: тренеры, клиенты, тренировки,
  заявки, оплаты (в боте / наличными), бесплатные периоды, топ тренеров;
- 👥 пользователи: все, кто писал боту (тренеры / клиенты / без регистрации),
  новые, активные (DAU / WAU / MAU, «уснувшие» 30+ дней), заблокировавшие бота
  (по `my_chat_member`), конверсия «пробный период → оплата»;
- 📈 графики (PNG, matplotlib): новые пользователи, активность и блокировки,
  выручка, занятия всех тренеров;
- 👨‍🏫 тренеры: карточка-отчёт, выдача подписки (оплата наличными по тарифу или
  бесплатный период на N дней), блокировка, рассылка его клиентам;
- 👥 клиенты: поиск по имени/телефону/@username/ID, блокировка;
- 📢 рассылки: всем тренерам / всем клиентам / всем / клиентам тренера — любой
  контент, батчами через taskiq, отчёт о доставке админам;
- ❓ FAQ двух видов (для клиентов и для тренеров);
- 📥 CSV-выгрузки: тренеры, клиенты, тренировки, подписки и оплаты.

Заблокированные админом пользователи получают «Доступ ограничен».

**Ещё не реализовано:** реферальная программа, онлайн-оплата, AI-функции.

## Стек

- Python, aiogram + aiogram_dialog
- PostgreSQL + SQLAlchemy (async) + Alembic
- Redis — FSM-хранилище диалогов + брокер и schedule source для taskiq
- taskiq — фоновые задачи и планировщик (генерация календарного буфера по cron,
  инфраструктура под отложенные напоминания)
- dishka — DI-контейнер

## Архитектура

Чистая архитектура, слои:

- **domain** — сущности (`Trainer`, `Client`, `Booking`, `CalendarSlot`, `SlotTemplate`,
  `TrainerInviteLink`, `TrainerSubscription` и др.), доменные сервисы (`CalendarService`),
  интерфейсы репозиториев, доменные исключения. Ничего не знает про БД/telegram/очереди.
- **application** — use case'ы поверх `Mediator`, оркестрируют domain через интерфейсы.
  Каждый use case — пара `Request` (dataclass) + `UseCase[Request, Result]`.
- **infrastructure** — SQLAlchemy-модели и реализации репозиториев, taskiq broker/worker/
  scheduler, DI-провайдеры (dishka), реализация `BookingScheduler`/`TaskQueue`.
- **presentation** — aiogram + aiogram_dialog: диалоги регистрации, бронирования, меню;
  роутер `/start` с обработкой deep-link токенов инвайт-ссылок.

## Как это работает — ключевые решения

**Календарь.** Тренер задаёт шаблон регулярных слотов (`SlotTemplate`, день недели +
время). Ежедневная taskiq-задача поддерживает буфер реальных `CalendarSlot` в БД на
~60 дней вперёд — ровно материализованные записи, а не "виртуальные" слоты, потому что:
на них держится блокировка тренером конкретных дат/слотов, и на них же держится
атомарность бронирования (защита от одновременной брони одного слота двумя клиентами).

**Регистрация.** Клиент попадает в бота только по персональной ссылке тренера
(`/start <token>`) — токен ищется в `TrainerInviteLink`, клиент привязывается к
конкретному `trainer_id`. Повторный вход по чужой ссылке не перепривязывает клиента —
он просто возвращается в меню своего тренера.

**Партнёрская модель (задел на будущее).** `Trainer`, `TrainerSubscription`,
`TrainerInviteLink` спроектированы с расчётом на нескольких тренеров с первого дня,
хотя в MVP активен только один — это позволяет не переписывать модель данных, когда
появится реальное партнёрство.

## Локальный запуск

Требуется PostgreSQL и Redis (например, в Docker).

```bash
uv sync
uv run alembic upgrade head
uv run python -m src.main          # бот
uv run taskiq worker src.worker:broker       # воркер фоновых задач
uv run taskiq scheduler src.scheduler:scheduler  # планировщик (cron-генерация календаря)
uv run uvicorn src.presentation.web.app:create_app --port 8080 --factory  # webhook ЮKassa
```

Тесты и проверки:
```bash
uv run pytest                 # все слои; PostgreSQL поднимается встроенным pgserver
uv run ruff check src tests
uv run pre-commit install     # один раз: ruff + pytest перед каждым коммитом
```

Тесты разложены по слоям: `tests/domain`, `tests/application` (use case'ы на
фейках), `tests/infrastructure` (репозитории, миграции, уведомления — реальный
Postgres), `tests/integration` (use case'ы через DI-контейнер и БД),
`tests/presentation` (прокликивание диалогов через `aiogram_dialog.test_tools`).
Внешние системы (Telegram, taskiq, Redis) в тестах подменены фейками.

Бизнес-параметры (часовой пояс, тестовые режимы напоминаний, сроки предупреждений
о подписке и т.д.) задаются в `.env` — см. `APP_CONFIG__BUSINESS__*` в `.env.dist`.

Расписание: время, убранное тренером из шаблона, делает будущие слоты неактивными
(`is_active=false`) — их не видят клиенты, но существующие записи сохраняются.
`status=BLOCKED` — только ручная блокировка тренером («🚫 Блокировка дней/слотов»).
